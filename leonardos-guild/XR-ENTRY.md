## Implemented change

Four real HTML buttons precede the narrative: VR first person, VR diorama, AR first person and AR diorama. The pause screen has the same four. Buttons exist before JavaScript/game initialization, are not replaced by a dropdown, and remain visible when a browser does not support XR. The original on-screen game remains a primary button. Secondary theatre/select controls remain for compatibility and inspection, below the primary choices. Controller focus order follows the primary choices rather than jumping to secondary settings.

Every direct click invokes the named requestSession synchronously within that browser activation, without first awaiting audio, a capability probe, a remote import, or another request. There is one session owner and one existing renderer. The game starts/resumes through its existing handler only after successful session setup and a tracked rendered frame; there is no second mandatory Start dialog. Generic retained theatre entry keeps its old manual-start behavior.

VR and AR support are checked independently. HTTPS, absent navigator.xr, and denied embedding policy have distinct explanations. An unavailable mode stays visible and disabled with a reason; a failed or slow capability probe is unknown rather than a permanent false unsupported verdict. Such a browser can still make a direct user-initiated attempt. A support recheck never requests consent or starts a session.

Permission rejection, unsupported mode, interrupted initialization and rendering failure produce persistent visible error text with the actual error name. Rejection rearms entry and does not retry or change mode silently. Late end events cannot clean up another session. The existing view, controls and saves are restored on exit. A startup watchdog ends an initialized session that produces no tracked frames rather than reporting success. There is no watchdog cancelling an open browser permission prompt. Physical room collision is not implemented, and first-person AR still requires a clear stationary play area.

## A-Frame assessment

A-Frame is an abstraction over Three.js and WebXR. Its documented xr-mode-ui supplies AR/VR entry controls and permits custom ones, but does not supply this game's player-centered portal or make browser support, secure contexts, permission and activation requirements disappear. A migration would need deliberate ownership of the scene, renderer, input and animation loop, not an a-scene surrounding a second running renderer. This repair retains the current renderer and implements the missing entry behavior directly. It does not claim an A-Frame conversion or preclude a later separately validated migration.

Primary references checked: https://aframe.io/docs/1.7.0/introduction/developing-with-threejs.html ; https://aframe.io/docs/1.7.0/components/xr-mode-ui.html ; https://aframe.io/docs/1.8.0/introduction/faq.html ; https://www.w3.org/TR/webxr/ . Documentation about the framework is not evidence that this game works on physical hardware.

## Page versus immersive visibility

A further lifecycle review found a real logic gap: app.mjs paused and suppressed simulation/audio whenever the browser document was hidden, even if the XR session remained visible. WebXR explicitly distinguishes immersive-session visibility from document visibility. The application now uses the initialized, non-ending session's visible state for immersive play, while ordinary on-screen play continues to obey document visibility. Losing 2D window focus no longer pauses a visible immersive game. Headset overlays, hidden sessions, lost tracking and session exit retain the existing pause/input-release rules. This is a code-level defect and supported platform scenario, not a claim that the owner's physical symptom has been reproduced.

Two added CPU tests bring the suite to 373 checks. The entry journey separately emulates browser document hiding and XR visibility for every one of the four modes. It requires continued real stick-driven player movement while the immersive view is visible, pauses on an XR overlay, and retains ordinary desktop page-hide pausing. The amended entry journey has 50 assertions; final native results, not this intended count, determine acceptance. The platform fixtures do not assign game state or time.

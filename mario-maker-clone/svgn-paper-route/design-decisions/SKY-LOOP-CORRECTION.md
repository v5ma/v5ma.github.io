# Sky-loop gameplay correction

The primary game is a real 3D side-scroller through a sky maze of launch loops. Delivery is an objective within that traversal, not a replacement street platformer. This correction implements the user's explicit September 4 direction and the earlier saved loop/curve/renderer requirements. The three street routes remain in campaign.js as legacy data; sky-routes.js deliberately replaces the primary menu's campaign.

First Flight has four full loops and three detached transfers. Cloudline Junction has five full loops and Aurora Express has six. Advanced courses include a lower alternate receiver whose exit rejoins the main launch lip. Only the small original launch pad and final depot have solid floor. A course requires completing its loop stages and transfers as well as the delivery quota. Holding right alone circles the loop; it cannot trigger an exit or win.

D/right throttles along the rail. A/left brakes on a rail and steers left in the air. Space arms the exit only while the rider is in the gold sector. The rider completes the circle, follows its physical exit ramp, and receives a tangential rocket boost at the lip. The ensuing flight uses velocity and gravity. A swept segment test detects the moving rider crossing the receiving rail; no position assignment transfers a rider between disconnected tracks. R retries the last caught loop. The visited-loop selector allows returning for a missed delivery. These deliberate checkpoint actions count as attempts.

C retains the original fixed-speed sector throw and inherited horizontal momentum. The sky route shortens the paper cooldown for usable delivery windows at launch speed. Mailbox hits still require actual packet collision. No computed hit solution or guaranteed delivery is added.

SkyVisual extends the existing WebGPURenderer scene with actual volumetric tubular rails, cross ties, gold exit markers, launch hardware, cloud banks, labels, and a speed trail. The existing voxel courier and vehicle remain 3D. Camera look-ahead and framing depend on speed but do not reduce graphics quality. The 2D view remains a fallback, not the primary renderer or the basis of 3D acceptance.

The existing editor and saved blueprint are retained. Edit route copy exposes the current sky tracks in the original editor. The optional cm field stores sky metadata alongside ct points and existing ca handles; launch regions are stored as length ratios so a scale transformation can preserve them. Arbitrary edits can make a route impossible: the editor does not claim automatic reachability proof. Existing non-sky levels retain the original physics.

Verification must use tests/sky_browser.py through native HTTP with the actual renderer. It records normal button/keyboard input from spawn to depot, rather than setting player position, velocity, track, score, or progress. Its report and video are the evidence of completion for a given commit. It also checks a right-only negative case, pause, restoration of the original blueprint, and serialization of copied sky tracks. The isolated local harness is useful for tuning but is not a WebGL or hosted-playability claim. Physical phones, controllers, and native WebGPU hardware require separate testing.

Technical reference: https://threejs.org/docs/pages/WebGPURenderer.html and https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame . This build retains the existing pinned renderer distribution rather than silently replacing it with a new release.

No dinosaur or theology application source is intentionally changed. The shared homepage copy is updated to describe the actual sky game. The earlier verification workflow retains its dinosaur/wiki checks and replaces its street-game component fixture with the new full 3D input replay. The feature workflow records integrated source on its own branch before running the tests. Rollback is a revert of the eventual squash merge, not a reset of unrelated master history or browser data.
